# Cgroup-256 fixes A–C Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix multi-process discovery so `profile --cgroup /` finds providers: decode each unique table once, make the 256 cap measured/configurable/documented with reusable view IDs, and scan all pids in two phases.

**Architecture:** Budget-owned admission stays the choke point; an Engine-side decode cache keyed by table identity removes repeat decodes; the pid cap becomes an Engine field fed by a CLI flag; view-ID allocation gains a free-list fed by existing view-removal sites; the initial scan splits into a maps-only sweep plus deep-scan of unique candidates.

**Tech Stack:** Rust 1.88 (`cargo +1.88`), clap-free hand-rolled CLI (`src/cli.rs`), existing `engine_tests.rs` fixtures.

**Spec:** `docs/notes/2026-09-16-cgroup-256-trace-everything.md` — the plan argues from it; executors read both. The kill chain (every GNOME proc re-decoding libp11-kit burns the shared 512-candidate budget) and the measured numbers (15.5s/0 probes cgroup vs 172ms/272 probes single-pid) are the acceptance authority.

## Task 1: Fix A — charge each unique table once (corrected design)

**Why this text replaced the original:** the first implementer fired the Step 1 tripwire and proved, line by line (report: `.superpowers/sdd/2026-09-16-cgroup-256-abc/task-1-report.md`, controller-verified): (a) a cached `ScannedModule` cannot be returned cross-view — `view` (engine.rs:4917) and `mount_namespace` (engine.rs:4918) are per-view stamps and `pin_scanned_view_objects` hard-errors on mismatch (identity.rs:1357–1358, propagated via `?` at engine.rs:8042), turning the first cache hit into a batch error; per-record `exports`/`interfaces` (engine.rs:4903–4925) also break a naive key. (b) The prescribed loader-route test never reaches `lower_export_record` (dispatch at engine.rs:11166–11181 routes LOADER to the memory-scan path). (c) The measured kill chain (0 probes attached) burns the budget entirely in the memory-scan path (`decode_candidate` → `admit_table` at scan.rs:699), so an export-path-only cache cannot fix the symptom. The design below fixes the root cause at the choke point both paths share: admission charging.

**Files:**
- Modify: `src/discovery/scan.rs` (`TableIdentity`, `CaptureWorkBudget.admitted_tables` + query/record methods near `admit_table` at line 388, `decode_candidate` admit site at 699, `table_candidates_count()` observer); `src/discovery/engine.rs` (export-path admit site at 4856 only).
- Test: `src/discovery/scan.rs` tests module + `src/discovery/engine_tests.rs`.

**Interfaces:**
- Consumes: `budget.admit_table(entries)` (signature unchanged — existing callers and tests keep compiling); identity components available pre-admit at both sites (device+inode+file_offset from `maps.resolve`, version word, usable/field count).
- Produces: `pub(crate) struct TableIdentity { device, inode, file_offset, version_word, usable }` in scan.rs (field types match `Resolved::File`/`ObjectKey` — verify while implementing; derive `Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord`); `CaptureWorkBudget.admitted_tables: BTreeSet<TableIdentity>` with `pub(crate) fn table_already_admitted(&self, id: &TableIdentity) -> bool` and `pub(crate) fn note_table_admitted(&mut self, id: TableIdentity)`; `pub(crate) fn table_candidates_count(&self) -> usize` observer. Task 4 consumes `TableIdentity` for candidate uniqueness. Call-site pattern at both admit sites:

```rust
if !budget.table_already_admitted(&id) {
    if !budget.admit_table(entries) {
        return /* today's refusal path, unchanged */;
    }
    budget.note_table_admitted(id);
}
// ... today's decode runs unchanged, per view, with a correct per-view result ...
```

Semantics: byte-identical repeats skip the candidate+entry charge but still decode per view — published results are unchanged, only spurious refusals disappear. The work-unit charge (`budget.charge`) is untouched: CPU is really spent. A full skip-the-decode cache is explicitly NOT this task (per-process addresses need re-stamping; revisit only if post-fix measurement shows CPU binding).
