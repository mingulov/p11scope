# Task 3.1 audit F1: burst-envelope loss — measurement, fix, requalification

Date: 2026-09-20. Branch `task-3.1/audit-f1-envelope`, base `5cad00c34377bf9953221af9b0b014fae49e7599`
(repair tip). Audit dir treated read-only; its evidence is not rewritten here.

## Outcome: FIX (both halves required), envelope requalified

E-burst is lossless again, at a corrected default. Two changes, each proven
necessary by measurement:

1. **Readiness wait**: the capture-loop idle wait polls the EVENTS ringbuf fd
   (wake on first record) with the same 2 ms timeout, instead of a fixed
   `thread::sleep`. A fixed sleep is a requested wait, not a scheduling bound.
2. **Default ring 256 KiB → 4 MiB** (780 → 12483 records). At unpaced burst
   rates (~128k/s) 780 records overrun in ~6 ms — inside routine scheduling
   jitter; 12483 need ~98 ms.

Requalified E-burst envelope (replaces the unconditional-lossless claim at
256K in `2026-09-20-task-3.1-loss-shares.md:189`):

- pid/profile, N ≤ 20000 unpaced, **default ring (4 MiB, 12483 records)**,
  reference 12-CPU desktop, ≤24 CPU-burner contention: **lossless, 10/10**
  (6× load24 with load1 up to 43, 2× load12, 2× ambient).
- Explicit `--ring-bytes 256K` is **outside** the envelope: the fixed binary
  still loses there under load (4445 once in 3 audit-verbatim repro runs), so
  the readiness wait alone does not save 256K. 1M is outside too (619 lost on
  base under load24; not requalified).
- No unconditional claim: a finite ring plus an adversarial scheduler can
  always overflow; `max_inter_drain_gap_ms` + capture/detach loss splits in
  evidence expose it. Contention bound is measured (24 spinners), not universal.

Findings (all windows valid; detach loss 0 everywhere; budget exhaustions 0):

- Audit reproduced on base: loaded 256K loses (977, then 6982 with only a
  7 ms max gap — instantaneous producer rate, not average, overruns the ring
  during short involuntary deschedules). Ambient survived 3/3 here while the
  audit caught one ambient loss: the outcome is a scheduling race, exactly as
  the audit ruled (non-monotonic, no claim every run loses).
- Contention sweep: 0×(0,0,0) / 12×(0,389,5502) / 24×(977,6982,6281). Variance
  itself is the signal: no margin at 780 records.
- Rate sweep: the pace knob is binary on a loaded box — any `pace-us ≥ 1`
  deschedules per call (`usleep` in the workload) and collapses to ~1.3–3.5k/s
  (5/5 lossless); unpaced spans ~10–119k/s. No intermediate rate is reachable,
  so the map is (unpaced, stochastic) vs (paced, lossless).
- Ring sweep: 1M still loses under load24 (619); 4M survives 3/3 including
  174–241 ms max gaps. Capacity, not the 2 ms constant, carries the point.

## Phase 2 — decision: FIX, both halves (numbers above and below)

- Wait-alone insufficient: fixed binary at explicit 256K still loses under
  load (4445; §requalification). Involuntary deschedule dominates; no wait
  primitive fixes a 6 ms overrun budget. So the 2 ms-poll repair cannot hold
  at 256K under contention — the audit's mechanism stands.
- Capacity-alone (4M on base) survived 3/3 but keeps the voluntary-sleep
  defect: a burst landing mid-sleep waits out the sleep while queued. The
  readiness wait removes that component for real (wake on first record; eBPF
  submits with flags 0 so every commit wakes waiters — verified at
  `crates/ebpf/src/main.rs` `EVENTS.reserve/submit(0)`).
- Drain-on-own-thread rejected: on the pid/profile burst path the per-tick
  non-drain work is already ~nil between 1 s frames, and a second thread gets
  no scheduling preference under SCHED_OTHER + spinners; it would add a
  consumer/ordering hazard for no measured gain.
- RT priority / nice rejected: the backlog path intentionally busy-loops
  (zero sleep); RT would let a hot ring starve the box. Out of scope.
- Narrowing (paced-only envelope) unnecessary: the fix holds 10/10 including
  6/6 under 24-worker contention with load1 to 43.

## The fix (tip `03c7feded15e17eaf0b1e3eb5ec57b46d905a472`)

- `src/events.rs`: `AsFd for EventsDomain` (retained EVENTS map fd).
- `src/attach.rs`: `Session::events_readiness_fd()`.
- `src/run.rs`: `wait_until_ready(fd, timeout)` via `libc::poll(POLLIN)` —
  same timeout the sleep used (`ready_sleep_duration`, 2 ms cap kept), zero
  still never blocks, EINTR returns to the tick checks (strictly faster
  signal response than sleep), unexpected poll errors fall back to the old
  sleep. Both capture loops (profile + trace) use it. Single consumer and
  discovery-before-semantic-consumption ordering preserved; poll consumes
  nothing. Comments updated (the "no epoll" line now names the poll wait).
- `crates/ebpf-common`: `RING_BYTES` 256K → 4M + pins; `src/cli.rs` docs.
- Oracle tracks the binary: `system-scope-measure.py resolve_ring_bytes`
  default → 4M (else default-path records get a spurious ring-mismatch
  method warning and trace streams the wrong capacity); loss-share test pin
  updated. `check-capture-evidence.py` needs no change (range-validates).
- Frozen BPF map inventory (`check-bpf-map-defs.py` SAFE_MAPS EVENTS
  262144 → 4194304): intentional contract change with the default-ring
  commit; the embedded object rebuilds with the new size (verified: the
  inventory test failed with `object=4194304 frozen=262144` before the
  freeze update, passes after).
- Tests: replaced the arithmetic-only oracle (green under the audit's 50 ms
  sleep mutant) with pipe tests pinning wake-on-data, mid-wait wake, timeout
  blocking (anti-spin), zero-timeout nonblocking, plus a requested-wait
  margin test that states explicitly it is not a scheduling proof. Mutation
  checks: sleep-always mutant fails the 2 wake tests; return-immediately
  mutant fails the timeout test.

## Residual concerns

1. The lossless claim is measured (10/10, contention ≤ 24 spinners on the
   reference box), not proven: worst observed involuntary gap is 427 ms and
   the differential producer−consumer rate under contention is unbounded in
   theory. A hostile scheduler can still overflow 12483 records. The
   envelope states the measured contention bound; evidence exposes any break.
2. `max_inter_drain_gap_ms` spans the whole capture including idle, so large
   gaps in lossless runs are expected and the metric cannot isolate
   burst-window scheduling. A burst-window-scoped gap (producer-alive only)
   would sharpen future envelopes; not added here.
3. Instantaneous producer rate is not instrumented — only the burst-window
   average. The rep2 case (6982 lost, 7 ms max gap) is attributed to
   instantaneous rate by elimination (no budget exhaustion, no repolls, small
   gaps); consistent, but a per-slice producer rate would make it direct.
4. Default ring memory is now 4 MiB per capture (plus the unchanged 64 KiB
   discovery ring). Negligible on desktop; noted for constrained targets.
5. `wait_until_ready` falls back to sleep on unexpected poll errors: silent
   by design (per-tick logging would spam). The fd is the capture-owned map
   and cannot fail in practice; any future failure mode degrades to exactly
   the old behavior.
