# Task 3.1 loss shares: why the event path loses data

Tree `8973935` (clean), release binary, host `7.0.0-31-generic`
AMD Ryzen AI 9 HX PRO 370 x12. Owned gated SoftHSM2 workload
(`system-scope-measure` harness + `BURST`/`TRUTH` oracle), seed 1.
Records: `/var/tmp/p11scope-31-*/{*/record.json,*/summary.txt}`,
run log `/var/tmp/p11scope-31-campaign.log` (35 entries, all rc=0).
Box load 3–5 throughout (sibling workers active); every run records
go-time loadavg. Burst-model points are load-insensitive by
construction; sustained points repeated — reps agree to ±1 count.

## Verdict: loss shares, ranked

Loss is kernel ring-buffer reserve failure (`event_loss`), nothing
else: every run's books balance exactly
(`kernel_observed − delivered == event_loss`, and for trace
`stats_returned − raw_calls == event_loss == last LOST`). What fills
the ring faster than the drain empties it decomposes as follows
(detail + raw numbers below):

| share | regime where it dominates | measured magnitude |
|---|---|---|
| ring-vs-burst (capacity) | any burst completing inside one inter-drain gap | loss = N − capacity, digit-exact (7/7) |
| drain cadence | sustained rate above capacity/gap | 1378/s: 8303 lost @1 s → 0 @200 ms (same ring+rate) |
| sink backpressure (trace) | sustained trace to a slow sink | 0 → 17191 (86%) file→4 KB/s pipe, same rate/ring/cadence |
| detach window (undrained) | production during detach taper | 7707 of 14101 (55%) in the split probe; 5847 pure-detach |
| discarded may-remain (quantum) | big ring + sustained overload only | 6832 @4 M/4872/s/1 s; exactly 0 at default ring (780 < 4096, proof by construction) and 0 for all bounded bursts |
| tick work (discovery on capture thread) | system scale | 667 ms user/tick stretches gap 1.0→1.69 s (×1.69 loss inflation); pid tick work 2 ms (≈0) |
| sink backpressure (profile) | — | 0 (±2 counts): frame volume « pipe buffer |
| mode (profile vs trace) | — | 8303 vs 8331 at equal cadence (≈0; tick-phasing noise) |

Dominant mechanism overall: **the ring must absorb a full inter-drain
gap's production, and the gap is 1 s (profile) with a 780-record ring
plus 0.67 s of discovery work at system scale** — i.e. ring size ×
drain cadence, exactly the prime suspect, with backpressure (trace
sinks, detach window) and the quantum corner as measured secondary
terms. There is no unexplained residual anywhere: every count is
attributed to a counter or a tick.

## Oracle and model

One `EVENTS.reserve` per completed call (return path only;
`crates/ebpf/src/main.rs`, reserve-after-stats), so aggregate-map
counts are ring-independent and loss is tail-drop (head-kept: the
first 780 records survive, verified by line order). Record footprint
336 B (328-B `Event` + 8-B header) → capacity = ring_bytes/336:
64 K→195, 256 K→780, 1 M→3120, 4 M→12483, 8 M→24966. Two regimes:

- Burst (wall < gap): loss = max(0, N − capacity), cadence-independent.
- Sustained (rate R, gap G): loss ≈ max(0, N − ticks×C) while
  R×G > C; lossless iff R×G < C (per-gap production fits).

Effective rate comes from `BURST` timing, never `--pace-us`
(`usleep` oversleeps ~200 µs: pace 500/2000/125/10 → 1378/440/3023/
4905 calls/s). Unpaced observed rate ~114k calls/s; the same workload
unobserved (refused provider, G1) runs 1.1M calls/s → ~8 µs/call
probe cost as a side datum.

Structural facts the shares rest on (all verified live): pid
captures end at target exit (2 frames: tick 0 + terminal); the
terminal drain is unbounded but runs after the detach taper (~60
ms/link strace-measured: ~8 s pid, ~61 s system) during which the
ring is undrained; `LOST` lines are cumulative (last wins), not
deltas; trace loss identity holds exactly on all 6 trace runs.

## Mechanism notes (evidence for each share)

- Ring-vs-burst: A1–A5/B1. Loss = N − capacity to the digit;
  delivered = capacity exactly. Cadence-irrelevant (burst wall
  0.16–0.19 s « 1 s gap).
- Cadence: C2→C3 (8303→0, only the gap changed) and C2→E4b→E4
  across modes. Faster cadence is nearly free here: 1 s→50 ms
  adds ~0.35 s CPU over 24 s wall (2.05→2.2 sys, 0.05→0.23 user).
- Quantum/may-remain: binds iff backlog > 4096 at a live tick.
  Default ring: impossible (780 < 4096) — share exactly 0,
  including F-Scale-3's regime. Bounded bursts: terminal drain
  (unbounded) absorbs the backlog — share 0 (A4: no live drain
  even ran post-burst; F2: binds every tick, still lossless).
  Sustained big-ring overload: 6832 in F2b, 100%
  quantum-attributable (same cadence/ring/rate + re-poll ⟹
  lossless is airtight: P=4872 < C=12483).
- Trace sink backpressure: E4→E3 (0→17191, wall 32→48 s):
  synchronous per-line writes into a 4 KB/s pipe against ~116 KB/s
  of line production (~30× over demand) stretch the effective gap
  until the ring stays full. Burst loss is sink-independent (E1=E2).
- Profile sink: file=discard=slow-pipe (8303/8305/8304):
  16-frame volume (~12 KB) never fills the 64 KiB pipe buffer —
  share 0 with mechanism (decoupling), not luck.
- Tick work: pid 1 ms user + 1 ms sys/tick (C2) → gap stays
  1.00 s. System 667 ms user + 35 ms sys/tick (G1; profile and
  metrics identical to 0.02 s) → gap stretches 1.0→1.69 s.
  Split: drain+reduce ≈ 0 (profile−metrics delta), render ≤
  ~1 ms (pid bound), map reads ≤ 35 ms sys → **discovery ≈
  666 ms/tick (39% duty)** sharing the capture thread.
  Loss inflation ×1.69 vs nominal gap at system scale.
- Detach window: no ticks, no drains, producers live until
  their link closes. G4m-2 split (timestamped LOST): 6394
  capture-tick + 7707 detach-window (55%) of 14101; G4m-1:
  5847 pure-detach, silent until the terminal LOST. G4m-1 is
  single-source: its raw artifacts lived only in the shared
  workdir `/var/tmp/p11scope-31-g4manual` and were wiped when
  the G4m-2 run executed tsprobe.sh's `rm -rf $W` — no record
  dir contains them, so the 5847 row survives only in this
  note. The 55% headline does not depend on it: G4m-2's
  timestamped record (`stdout-ts.jsonl`: 11 tick LOST lines
  ending 6394, a 10.7 s silence gap, terminal 14101) is the
  independent evidence. Fixed prospectively: `scripts/
  tsprobe.sh` is now committed with per-cell workdirs and an
  ownership guard (`--self-test` pins it), so a re-run cannot
  wipe a sibling cell again. Terminal drain keeps exactly one
  ringful (780). F3a/b vs F3c: 4 M absorbs detach production
  (0 loss), 256 K drops ~half of it.
- Discovery ring (context, owned by 3.1b): separate 64 KiB
  ring (~70 records), drained per tick on the same thread;
  G1/G2/G3 lost 4112/4140/2372 loader records — churn-bursty,
  independent of `--ring-bytes` (EVENTS only). Dwarfes EVENTS
  loss at system scale today.
- System foreign traffic: G1 event_loss=194 (fork-churn
  bursts overfilling 780 between 1.69 s ticks) → 0 at 1 M
  (G2); G3 caught no storm (0). Sporadic; discovery loss is
  the steadier system signal.

## F-Scale-3 retro-diagnosis

F-Scale-3 (pre-Phase-1 tree, full call coverage): 2620 lost/30 s
profile, 1996/15 s trace. That regime is admission-gated today:
post-1.2 K=4 admits 410 dormant p11-kit slots and refuses the
active workload provider (G1: 0/20002, same as 1.4), so the
current system ring carries fork-churn (~194/120 s), not calls.
F-Scale-3's 2620 therefore does NOT replicate numerically — but
it decomposes cleanly with the measured model: sustained call
rate × (1 s + 0.69 s discovery stretch) overfilling 780 records
per gap, plus a ~40 s undrained detach tail. Every term of that
decomposition is now measured; only the pre-1.2 input rate is
historical.

## Repair handoff (must-know)

1. The aggregate maps are the window proof (ring-independent);
   never validate a window from delivered lines/counts.
2. `LOST` is cumulative; per-tick deltas need timestamping.
3. The terminal drain is unbounded — size it or bound it
   explicitly; today it silently absorbs ≤1 ringful post-detach.
4. Detach is 60 ms/link with zero drains — drain during
   detach or count the window separately.
5. Trace's 200 ms default already beats profile's 1 s 5× at
   equal cost — cadence, not mode, is the lever.
6. Discovery costs 666 ms/tick on system — the drain path
   cannot share the thread with it at scale (3.1b).
7. The multi-wrapper fixture (`tests/fixtures/multi-wrapper/`)
   cannot produce a loss share: its scenarios emit ≤120 calls
   (five=120, holes=26, pair=52, legacy=0 — 1.4 oracle
   numbers), all below the 780-record single-gap capacity, so
   it is the admission oracle, not a load generator. The
   system-scope gated workload (N ≤ 100000, rate-controlled,
   exact TRUTH) is the owned counting fixture for the event
   path; live `--system` points (G1–G3) carry the foreign/
   churn/scale terms instead.
