# pkcs11-scope v0.1 corrective release — design

**Date:** 2026-08-12

**Status:** Approved as amended; implementation pending

**Input:** `docs/notes/2026-08-12-code-review-max.md`

**Privacy amendment:**
`docs/superpowers/specs/2026-08-13-safe-and-unvalidated-metadata-design.md`
supersedes this document's mechanism/template capture and observed-profile
schema rules according to the selected capture policy. All other corrective
requirements remain in force.

**Standard:** [OASIS PKCS #11 v3.2 Standard](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/pkcs11-spec-v3.2.html)
(3 June 2026), including its published

and
[`pkcs11t.h`](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/os/include/pkcs11-v3.2/pkcs11t.h).

## Goal

Fix every confirmed finding in the v0.1.0 code review and leave a regression
suite that fails for the original defect, including defects in the tests and
release gates themselves. Fix shared causes once; do not preserve an unsound
manifest or output contract merely to avoid a version bump.

Support is cumulative, never latest-only. The same release supports every
published `C_GetFunctionList` ABI through the PKCS #11 3.2 Standard: the
67-entry 2.00 table, the 68-entry 2.01 through 2.40 tables, the 3.0 and 3.1
92-entry interfaces, and the 3.2 104-entry interface. Here, "supports" means
discover, attach, count, and apply every profile-relevant mechanism/session
transition for every published ABI slot; it does not mean reading arbitrary
PKCS #11 data buffers, which remain outside the privacy boundary. PKCS #11
1.0 predates `C_GetFunctionList`, so it is not a function-table ABI and is
outside this table-driven observer's contract.

The 3.2 prose specifies 110 functions, but the final published headers expose
only 104 `CK_FUNCTION_LIST_3_2` slots. The other six are the
`C_DigestXof*` family and have no published function-list ABI entry. They stay
as explicit source-coverage gaps; this release neither invents attach slots nor
claims those six are observable. "Full 3.2 support" below always means all 104
published slots plus all published mechanism and attribute identifiers.

The prose also names 11 mechanisms for which final `pkcs11t.h` assigns no
numeric value: composite KEM (2), composite signature (3), KMAC (2), external
Mu ML-DSA (2), and SHAKE digest (2). A runtime observer sees only
`CK_MECHANISM_TYPE`, so these remain explicit no-published-value gaps; no
numeric constants are invented. All 463 unique mechanism values that the final
header does publish remain in scope.

The separate whole-repository security review remains a distinct Gate G5
activity. This corrective release fixes the privacy and trust-boundary findings
already validated by the code review; it does not claim that outstanding review
has happened.

## Design rules

- Aggregate BPF maps remain the authority for per-function counts. The event
  stream supplies semantic context only.
- Unknown, aliased, unreadable, or failed evidence is reported, never guessed.
- Provider code remains confined to the short-lived unprivileged discovery
  helper.
- Public JSON changes that alter meaning get new schema identifiers.
- The final OASIS 3.2 headers, verified through the pinned shared workspace,
  are the function/order and identifier oracles. Published ABI functions may
  be explicitly count-only, but none may fall through as unknown by accident.
- Tests use repository fixtures wherever possible. No new test framework or
  generalized abstraction is introduced.

## 1. Event capture and semantic state

### Explicit operation model

Replace the single `(pid, session) -> mechanism` binding with
`(pid, session, operation) -> mechanism`. The supported operation keys are
digest, sign, verify, encrypt, decrypt, sign-recover, verify-recover,
message-encrypt, message-decrypt, message-sign, and message-verify.
`C_VerifySignature*` uses the ordinary verify key, matching `CKF_VERIFY`, rather
than inventing a parallel verification state. Pending/cancellation descriptors
also name find-objects, generate, generate-key-pair, wrap, unwrap, derive,
encapsulate, and decapsulate classes, but those direct calls never create a
mechanism binding. Combined update calls name both operations they actually
advance. Unrelated session calls and object-search calls cannot be charged to,
or clear, a cryptographic mechanism.

Keep one separate `(process, session)` presence bit for an active object
search: successful `C_FindObjectsInit` sets it, successful
`C_FindObjectsFinal` clears it, and conclusive state errors reconcile it. This
bit carries no mechanism and never contributes mechanism calls; it exists only
so authentication teardown and `C_SessionCancel(CKF_FIND_OBJECTS)` have honest
state. Async direct operations need no parallel presence structure because the
pending record already is that state.

Replace the growing `fnkind` switch and `SLOT_KIND: Array<u32>` with one compact
`SlotSemantics` value per slot. It contains only fixed operation/transition
bits and allowlisted argument indices (session, slot, mechanism, output,
flags, and at most two template/count pairs). `ARG_NONE` represents absence;
only indices 0 through 6 are accepted and 7 or above are rejected before map
publication. This is data, not a new framework: descriptors are generated
exhaustively from the shared 104-field inventory.

Each attach slot therefore receives one userspace-derived semantic
description:

- operations affected by the function;
- transition: initialize, continue, finish-with-output, or finish-always;
- direct-mechanism operation, for key-management functions;
- session lifecycle action, if any.

This description is derived from exact function names. An alias slot is used
semantically only when every name yields the same descriptor; otherwise its
aggregate function count remains available but the state machine makes no
mechanism or lifecycle guess. Aliasing already forces `PARTIAL`.

Initialization records the requested mechanism even when the provider rejects
it. A successful initialization replaces that operation's binding. A failed
initialization leaves an already-active operation intact. Null-mechanism policy
is explicit per function, never inferred from the `*Init` suffix. The final
standard defines successful null cancellation for `C_EncryptInit`,
`C_DecryptInit`, `C_DigestInit`, `C_SignInit`, `C_SignRecoverInit`,
`C_VerifyInit`, `C_VerifyRecoverInit`, `C_VerifySignatureInit`, and
`C_MessageEncryptInit`; those calls clear only their named operation. It does
not define that behavior for `C_MessageDecryptInit`, `C_MessageSignInit`, or
`C_MessageVerifyInit`. If one of those three nevertheless succeeds with a null
mechanism, the observer clears its local binding, increments
`evidence.semantic_capture_failures`, and forces `PARTIAL` because the provider
state cannot be inferred safely. Any failed null init preserves the active
binding. A successful initialization whose non-null mechanism pointer could
not be read also clears the binding so later calls become explicit orphans
rather than inheriting stale evidence.
The event representation distinguishes descriptor-has-no-mechanism,
null-pointer, non-null-but-unreadable, and decoded mechanism; the 3.x
null-pointer cancellation rule must never be confused with a failed read.
Non-null mechanism-read failures and the single stack-argument read failure
increment `evidence.semantic_capture_failures` and force `PARTIAL`. A
successful init with an unreadable mechanism still clears its old binding;
direct calls remain counted but are not attributed to a guessed mechanism.

This deliberately reverses commit `201ee66` and replaces the regression later
strengthened by `585b81d`. Clearing every binding on every `*Init` was a
defensive workaround for the old one-binding-per-session model. With bindings
split by operation, that workaround is both unnecessary and wrong: a failed
call normally leaves provider state unchanged, and `CKR_OPERATION_ACTIVE`
specifically means an existing operation prevented the requested one from
being activated. The failed attempt is still recorded against its requested
mechanism; it simply does not replace or erase the existing binding.

Conclusive state errors override normal transition rules. If an
operation-specific call returns `CKR_OPERATION_NOT_INITIALIZED`, do not charge
it to a locally cached mechanism; clear the named binding (both candidates for
a dual call) or object-search bit, and record
`evidence.state_reconciliations` when local state had disagreed.
`CKR_SESSION_CLOSED` or `CKR_SESSION_HANDLE_INVALID` similarly
retires a matching tracked session, and `CKR_CRYPTOKI_NOT_INITIALIZED` retires
that process's tracked sessions. These reconciliations force `PARTIAL`: they
repair future attribution but prove an earlier transition or external action
was unseen. Other errors follow the exact function contract below.

Termination follows the PKCS#11 function contract, not name suffixes. These
buckets apply to completed returns; `CKR_PENDING` defers the same rule to async
completion. The function buckets are explicit:

- `C_Verify` and `C_VerifyFinal` are finish-always and clear verification on
  every return;
- `C_Encrypt`, `C_Decrypt`, `C_Digest`, `C_Sign`, `C_SignRecover`,
  `C_VerifyRecover`, `C_EncryptFinal`, `C_DecryptFinal`, `C_DigestFinal`, and
  `C_SignFinal` are finish-with-output. They retain their operation only for
  `CKR_BUFFER_TOO_SMALL` or `CKR_OK` with a null output pointer (a successful
  length query), and otherwise clear it;
- `C_EncryptUpdate` and `C_DecryptUpdate` retain on `CKR_OK` or
  `CKR_BUFFER_TOO_SMALL` and clear on other errors. `C_DigestUpdate`,
  `C_SignUpdate`, and `C_VerifyUpdate` retain on `CKR_OK` and clear on error;
- `C_DigestKey` leaves a valid digest binding intact on ordinary errors:
  unlike `C_DigestUpdate`, its contract does not make an error terminate the
  operation. The conclusive state-error reconciliation above still applies;
- `C_DigestEncryptUpdate`, `C_DecryptDigestUpdate`, `C_SignEncryptUpdate`, and
  `C_DecryptVerifyUpdate` retain both valid bindings. A null output pointer,
  `CKR_BUFFER_TOO_SMALL`, or another failure can prevent the secondary
  operation from receiving data, but none of these dual-function contracts
  says that the binding itself is terminated; conclusive state errors still
  reconcile both candidates.

For finish-with-output and output-update functions, the entry probe reads only
the pointer-sized argument selected by the descriptor, immediately reduces it
to a null/non-null boolean, and never stores or dereferences that pointer or
reads the output-length argument. The descriptor covers output argument 1 for
the four classic final calls and argument 3 for the six classic
one-shot/recover calls and output-producing updates.

Aya 0.2.1's x86-64 `ProbeContext::arg()` exposes only arguments 0 through 5,
while `C_UnwrapKeyAuthenticated` puts its allowlisted template count at
argument 6. A single `arg_u64()` helper uses `ctx.arg()` for 0..=5 and, only
for the checked index 6, reads one ABI word from the user stack at `rsp + 8`.
Arguments 7 through 9 are never read. No generic stack walk is added. A native
ten-argument fixture pins the SysV entry ABI, proves argument 6, and plants
negative canaries in 7..=9. The release remains explicitly x86-64 Linux;
another architecture needs its own live ABI fixture before it is claimed.
Argument-word reads, output nullness, and every per-function index get
privacy-allowlist rows and live canaries.

### PKCS#11 3.x operation semantics

The four `C_Message*Init` calls bind their own message-operation key on
successful non-null initialization. Their function-specific null-mechanism
behavior follows the rules above. `C_*Message`,
`C_*MessageBegin`, and `C_*MessageNext` are attributed to that binding but do
not clear it: they start/finish individual messages inside a process that stays
active. A successful `C_Message*Final` clears the process. The descriptor still
attributes every message call, including error and `CKF_END_OF_MESSAGE` cases,
to the process binding. It does not retain a second per-message substate because
that state changes no observed-profile result.

`C_VerifySignatureInit` binds the ordinary verify operation and never reads
its signature argument. Its successful null mechanism cancels ordinary
verification. `C_VerifySignature` and
`C_VerifySignatureFinal` always terminate verification;
`C_VerifySignatureUpdate` terminates it on error.

`C_SessionCancel` maps the exact standard `CKF_*` operation bits, including
the four message bits and generate/key-pair/wrap/unwrap/derive/encapsulate/
decapsulate bits, onto long-lived bindings and pending direct operations.
`CKR_OK` clears only the selected state, so canceling one half of a dual
operation leaves the other active. A single selected operation with
`CKR_OPERATION_CANCEL_FAILED` is known to remain active. With multiple selected
operations that result gives no per-operation answer; all selected bindings
are discarded to prevent stale attribution,
`evidence.session_cancel_ambiguities` is incremented, and the capture becomes
`PARTIAL`. Bits outside the standard operation mask are reported separately
and also force `PARTIAL`. Zero flags change nothing; other completed failures
leave state intact, and `CKR_PENDING` follows the async path below.

`C_GetOperationState` is counted but its opaque output is never read. A
successful `C_SetOperationState` can replace several active operations without
revealing their mechanisms, so it clears every known binding for that session,
increments `evidence.operation_state_imports`, and forces `PARTIAL`; a failed
restore leaves the known bindings intact. This prevents opaque restored state
from inheriting stale mechanism attribution.

### Direct key-management mechanisms

`C_GenerateKey`, `C_GenerateKeyPair`, `C_WrapKey`, `C_UnwrapKey`,
`C_DeriveKey`, `C_EncapsulateKey`, `C_DecapsulateKey`,
`C_WrapKeyAuthenticated`, and `C_UnwrapKeyAuthenticated` capture
`pMechanism` directly and record distinct operation labels. They never create
session operation state. The descriptor also covers all object templates that
describe requested policy: create/copy/get/set/find, key generation and
key-pair generation, unwrap/derive, encapsulate/decapsulate, and authenticated
unwrap. `C_GetAttributeValue` records requested types only; because its values
are outputs, it never reads `pValue` or `ulValueLen`. Two template pairs are
needed only for `C_GenerateKeyPair`; its event and output keep public and
private template roles distinct rather than merging their policy. All other
walks reuse the same bounded allowlist and never read non-allowlisted values.

### Session lifecycle

`C_OpenSession` records the input slot id, `CKF_ASYNC_SESSION` boolean, and the
returned session handle. The state machine tracks `(pid, session) -> slot` and
reports async-session opens without retaining unrelated flag bits.

- successful `C_CloseSession` retires one matching session;
- successful `C_CloseAllSessions(slot)` retires that process's sessions for
  that slot only;
- successful `C_Finalize` retires every tracked session for that process;
- process death retires every remaining session for that process.

Process death is tracked in userspace, beginning only when an event creates
semantic state for that process. At startup the privileged observer makes a
best-effort raise of the soft `RLIMIT_NOFILE` to the hard limit, reserves 64
descriptors for its ordinary work, and caps live pidfds at the smaller of the
remainder and 16,384. Pidfds are owned descriptors: successful Finalize,
explicit retirement of the process's last state, or process death removes the
tracker and closes its fd.

A full pidfd budget demotes the least-recently-used pidfd to a `/proc/<pid>/stat`
start-time tracker; `pidfd_open` failure uses the same fallback. The fallback
compares start time while polling, so later PID reuse is detected, and is
bounded by the same 16,384-process tracker limit. Reaching that overall limit
retires the least-recently-used process state and increments
`evidence.process_tracking_evictions`. A working fallback increments an
informational `process_tracking_fallbacks` counter but does not by itself make
the capture partial. Only inability to establish either tracker increments
`process_tracking_failures`; failures and state evictions are explained on
stderr and force `PARTIAL`. Pidfds close the reuse race after they are opened,
but the interval between the first event and establishing either identity is
unavoidable and is not claimed away. Raw process identifiers are not added to
profile JSON.

`sessions.closed` is broadened to mean sessions retired by any of the four
known teardown paths above. This makes `balance` mean sessions still live at
capture end rather than merely sessions lacking an explicit
`C_CloseSession`. Only `CKR_OK` `C_Login` and `C_LoginUser` calls contribute to
`logins`; both capture only `userType`. `C_LoginUser` never reads either its
PIN or username pointer/length.

Ordinary successful `C_Login`, `C_LoginUser`, and `C_Logout` may or may not
preserve active cryptographic and object-search operations. For those returns,
discard bindings, object-search presence, and non-detached pending state for
every tracked session of that process on the same slot. If any such state
existed, increment
`evidence.auth_state_ambiguities` and force `PARTIAL`; detached async records
retain their stable ids but lose their current owner. The exception is a
successful `C_Login(CKU_CONTEXT_SPECIFIC)`: the standard uses it to authenticate
an already-active key operation, so that binding is preserved. Ordinary failed
calls leave state intact, but `CKR_PIN_LOCKED` is treated like logout because
the standard says it also logs the user out. This prevents an unspecified
provider choice from becoming stale mechanism attribution without breaking
the `CKA_ALWAYS_AUTHENTICATE` flow.

### Fork-safe interfaces

The attach plan preserves each target's surface provenance and
`CKF_INTERFACE_FORK_SAFE` flag. State created through a target present only on
fork-safe standard surfaces is fork-safe; a target shared with legacy or a
non-fork-safe surface is ambiguous, not silently promoted.

For cgroup captures, a small `sched_process_fork` tracing program emits a
tagged record into the existing global ring buffer before the child can issue a
PKCS#11 call. Userspace clones the parent's proven-fork-safe sessions and
operation bindings to the child. Non-fork-safe state is not cloned; ambiguous
inherited handles are remembered, and only become
`evidence.fork_state_ambiguities`/`PARTIAL` if the child actually uses one.
Ring loss already makes this evidence partial. Exact-PID scope remains exact
and does not widen itself to children.

Inherited session copies get new child-local pseudonyms and increment
`sessions.inherited`; they do not inflate explicit `sessions.opened`.
`balance` becomes `opened + inherited - closed`, and process/Finalize teardown
affects only that process's copy. No polling-based reconstruction is used: it
would snapshot the parent's state after the fork and can race with parent
calls.

### PKCS#11 3.2 asynchronous completion

`CKR_PENDING` is an in-progress result, so a state transition cannot be applied
at the original return. The userspace state machine keeps a bounded pending
record keyed by `(process identity, session, exact standard function id)` with
the original descriptor, safe captured metadata, and start time. The function
aggregate still counts each API entry; mechanism attribution and lifecycle
transition are finalized exactly once when `C_AsyncComplete` returns the
original function's non-pending result. Aggregate function latency remains the
duration of each API call; semantic mechanism latency for a pending operation
runs from the original entry to final completion, and the schema documents the
distinction.

`C_OpenSession` is the one transition that can return `CKR_PENDING` before a
session is in the local model. On that return, the probe bounded-reads only the
scalar handle written through `phSession`. A readable nonzero handle keys the
pending open and carries its captured slot/async flag; the session is added
only when `C_AsyncComplete` returns `CKR_OK`. An unreadable or zero pending
handle increments `evidence.async_target_failures` and forces `PARTIAL`, since
the standard's completion API cannot be correlated without that handle.

For `C_AsyncComplete`, `C_AsyncGetID`, and `C_AsyncJoin`, BPF reads at most 32
bytes from `pFunctionName` into stack memory, accepts only a NUL-terminated
exact match from the 104-name standard table (the longest is 27 bytes), and
emits only the numeric function id. Raw name bytes and pointers never enter a
map or output. Unknown, overlong, or unreadable names increment
`evidence.async_target_failures` and force `PARTIAL` rather than guessing.

On successful `C_AsyncGetID`, BPF reads the returned scalar id and userspace
moves the matching pending record into a bounded detached map keyed by
`(slot, function id, async id)`; raw ids remain internal. The record retains its
current session owner so `C_SessionCancel` can still select it. Close,
close-all, Finalize, or process death cancels and removes every matching
pending record whose id was not retrieved, while clearing the owner of a
detached record without destroying it. Successful `C_AsyncJoin` assigns the
joining process/session without reading its data buffer. Successful
cancellation removes matching owned pending or detached records. Detached
records otherwise survive until join, completion, cancellation, or capture end
as the standard permits.
Duplicate keys, orphan complete/get-id/join calls, pending records at capture
end, and bounded-map eviction are explicit evidence and force `PARTIAL`. The
two pending maps share a 16,384-record ceiling and evict least-recently-used
records; no unbounded async state is introduced.

`C_GetSessionValidationFlags` and the two interface-management functions are
attached and counted with RV/latency, but their output buffers are deliberately
not read. The same is true for every other standard function whose arguments
do not contribute to the observed-profile contract: its descriptor is
explicitly count-only, never an accidental unknown.

### 3.2 identifiers and privacy boundary

Every standard 3.2 mechanism id from the shared
`PKCS11_3_2_OFFICIAL_MECHANISMS` oracle, and every vendor id, is retained
verbatim as `u64`; the parameter-shape registry may enrich an id but may never
filter it from observation. A mechanism with no allowlisted decoder is emitted
as id-only (`params: null`), not mislabeled unsupported. Likewise, every
successfully captured standard or vendor attribute type in an allowlisted
template position is retained numerically; the existing eight-entry bound and
read failures remain explicit `templates_truncated`/`PARTIAL` evidence rather
than silent filtering. Attribute values and mechanism parameters remain
limited to the existing explicit privacy allowlist. "Full 3.2 support"
therefore means no published function-list slot or captured identifier
disappears because it is unknown, not that the observer copies every standard
parameter structure or data buffer.

### Attach window

Raise `MAX_SLOTS` from 256 to 512. With no pointer aliases, one legacy 2.40
surface plus one standard 2.40, 3.0, 3.1, and 3.2 surface needs
68 + 68 + 92 + 92 + 104 = 424 slots; the old ceiling cannot represent the
supported matrix. The plan must refuse before BPF load, with required and
available counts, if provenance grouping still leaves more than 512 targets.
It never attaches an arbitrary prefix. A dynamic map-size mechanism is not
introduced for a bound the standard matrix does not require.

Load and attach `p11_return` before `p11_entry`. A return without a start is
already ignored. This removes the only ordering window that can create a
permanent start entry.

`START.insert()` uses `BPF_NOEXIST` and is checked. This detects both a full map
and a re-entrant same-thread/same-slot call instead of silently replacing the
outer start. Reuse the existing per-CPU loss array with named indices: index 0
remains ring-buffer reservation failures, index 1 counts failed `START`
inserts, index 2 counts failed `RV_COUNTS` updates, and index 3 counts cgroup
helper errors. Each is rendered separately and forces `PARTIAL` in both
profile modes; the counters explain cases where `entered` continues to rise
but return timing, return-value, or semantic evidence cannot be matched.

`RvKey.rv` becomes `u64`, matching LP64 `CK_RV`; vendor returns are not
silently narrowed to 32 bits. The bounded 4,096-key map remains sufficient for
normal use, but every update is checked and `evidence.rv_map_drops` makes
pressure visible rather than pretending the exact RV distribution is complete.

## 2. Cgroup scope

Delete lexical cgroup-level calculation and the id/level hash-map protocol.
Userspace opens the supplied cgroup directory and installs its file descriptor
at index 0 of Aya's existing `CgroupArray`. The BPF programs call
`current_task_under_cgroup(0)`, which asks the kernel whether the current task
is in that cgroup or a descendant. This is namespace- and hierarchy-aware and
does not depend on `/sys/fs/cgroup` path spelling.

Failure to open or populate index 0 aborts startup. In BPF, `Ok(true)` admits
the call and `Ok(false)` filters it; `Err` increments a dedicated per-CPU
`evidence.cgroup_scope_failures` counter before filtering. Any such error is
reported and forces `PARTIAL`, so a helper failure cannot render an empty
capture as complete.

The overall kernel floor remains 5.15 because every probe uses attach cookies;
the cgroup helper itself is not the source of that floor.

## 3. Discovery and manifest trust boundary

### Loaded-object identity

Discovery requires an absolute module argument; relative and basename-only
lookup are rejected. It records the argument path only when the loaded mapping
has the same device and inode as that path. `/proc/self/maps` device/inode
identity, not a `dlsym` address, distinguishes the requested module from
dependencies. This is also required at attach time: Aya independently resolves
basename-only objects (`is_basename_only`), so an absolute object path is what
makes the manifest identity and the later uprobe target agree. The documented
commands already use absolute paths.

The module object is seeded before function-pointer walking. A pointer mapping
with the module's device/inode uses that object; a pointer in a dependency gets
that dependency's own object and build identity. A path swap or identity
mismatch fails discovery rather than producing a reusable mixed manifest.

### Attach authorization and byte continuity

A stored manifest is never attach authority. `profile` and `trace` require an
independent operator-selected `--provenance-module`; there is no default back
to the manifest's path. Before either command builds a plan, the observer pins
every proposed attach object, acquires a Linux read lease, and hashes and
validates that same descriptor. Fresh table discovery follows the
review-corrected bounded closure protocol in
`docs/superpowers/plans/2026-08-13-manifest-provenance.md`: the helper
executable is pinned by fd, while the provider is loaded by its revalidated
absolute path so `$ORIGIN` remains correct. A preliminary pass inventories all
file-backed executable mappings; the parent leases them and repeats until one
complete pass used only exact device/inode objects represented by retained
lease fds before the pass began. A distinct byte-identical inode does not
satisfy stabilization and causes another bounded retry. Churn, unleaseable
mappings, or a changed seed module fail closed. Only that pass may provide the
canonical function-name/object-SHA/file-offset comparison; paths, ASLR
addresses, object IDs, and volatile diagnostics are ignored at that later
candidate comparison.

Provenance-closure leases remain through authorization comparison; candidate
attach-object leases remain through probe attachment and the complete capture.
The observer re-hashes after attachment and checks lease continuity before
draining or publishing output. An existing writer, unsupported lease, or lease
break fails closed. Before BPF load, the original CLI process remains a
minimal lease supervisor and forks a capture worker; only the worker may own
BPF fds. On a break the supervisor sends the worker uncatchable `SIGKILL`,
waits for its pidfd to prove process exit (and therefore closure of every BPF
link), and only then releases the last lease references and exits 78. Normal
shutdown likewise requires the worker to write final output, drop `Session`,
and exit before the supervisor releases leases. `PDEATHSIG=SIGKILL` is
best-effort fail-stop hardening for unexpected supervisor death, not the
ordering proof; host-root, kernel/OOM, and supervisor-crash termination remain
outside that proof. Numeric fd-close order is never the normal teardown
mechanism. The bounded protocol, signal-identity assumption, and failure cases
are specified in the linked provenance plan. Establishing a lease on an object
not owned by the observer requires `CAP_LEASE` (or root); hostile-target use
additionally requires a supervisor identity the workload cannot signal or
ptrace.

The authorization helper is a trusted sibling executable, opened once and
executed via `/proc/self/fd`; this fd path applies only to the helper, never the
provider. For a hostile target, the official fully static observer parses and
pins the helper's complete interpreter/recursive runtime closure before exec,
rejects preload/audit/RPATH and writable-path influence, and read-leases every
selected inode. It executes the pinned loader fd directly with cache-disabled
options, a root-owned non-writable but child-traversable fd-backed library
directory, empty environment, and the pinned helper fd as its program. A
control-fd handshake before `dlopen` confirms that the resulting pre-provider
maps contain exactly those pre-authorized inodes; it does not attempt to
authenticate constructors after they ran. Provider code still runs only after
UID/GID, groups, and capabilities are removed. The helper remains
non-dumpable; it opens `/proc/self/mem` as same-thread-group self access after
the drop rather than restoring dumpability. That mandatory oracle has no
inherited stderr channel, emits at most 16 MiB, and has a 30-second deadline
whose expiry kills and reaps its process group.
Dynamic-observer and unknown-loader launches are trusted-workload/refusal lanes,
not hostile-target authorization. If fresh provenance cannot be established
there is no raw-manifest bypass.

### Acquisition before maps

Call both `C_GetFunctionList` and `C_GetInterfaceList` first, preserving their
independent outcomes and returned table pointers. Snapshot `/proc/self/maps`
afterward so a wrapper that lazily loads its backend during acquisition is
represented before pointer resolution.

Parse maps as bytes: consume the five fixed whitespace-delimited fields, then
treat the remainder as the pathname so embedded spaces survive. Preserve
device, inode, permissions, offsets, and the raw pathname representation. Linux
renders a newline as the ambiguous bytes `\012`, indistinguishable from a
literal backslash sequence; any pathname containing that sequence is reported
unusable rather than decoded or guessed. An unrelated non-UTF-8 mapping cannot
abort discovery. Deleted, non-UTF-8, inaccessible, ambiguous, or
identity-mismatched file mappings become explicit unattachable resolution
evidence, including raw path hex where a string path is unavailable; they never
become reusable object paths.

### Shared-crate precursor

Reuse the existing `pkcs11-module` and `pkcs11-proxy-ng-types` crates from
`pkcs11-proxy-ng`; do not create a third catalog or a scope-specific copy. The
current crate split is already the right product boundary: `pkcs11-module`
owns raw acquisition, field offsets, and version-to-layout facts;
`pkcs11-proxy-ng-types` owns the official mechanism inventory; provider
selection, unnamed-interface fallback, and quirks remain proxy policy; pointer
provenance and evidence verdicts remain scope policy.

One precursor API correction is required in `pkcs11-module`. Its
`interface_list()` currently turns provider pointers into a `CStr` and a
`CK_VERSION` before scope can apply a bounded read. Change `RawInterface` to
return only `name_ptr`, `func_list`, and `flags`; enumeration copies the
provider-returned `CK_INTERFACE` records but dereferences neither target.
Scope then reads the name through `/proc/self/mem` with a 256-byte cap and a
required NUL, reads the two-byte version the same way, and records null,
unreadable, or overlong values as evidence. Exact `"PKCS 11"` classification
happens only after that read, but exact naming is not the only compatibility
path: deployed 3.x providers sometimes expose a standard-shaped table under
another name.

An exact `"PKCS 11"` entry uses the normal standard-version matrix. An entry
with another, null, or unreadable name is never trusted from its version stamp
alone. Scope may walk it only as a corroborated standard prefix when a bounded
snapshot places the module's actual exported `C_GetFunctionList` pointer in
the published base slot and, for a 3.x table, the actual exported
`C_GetInterfaceList` and `C_GetInterface` pointers in the two published 3.0
slots. A 2.40 alternate must instead match the independently acquired legacy
table pointer-for-pointer across all 68 fields. This makes accidental vendor
layout interpretation implausible without adding provider-name policy.

The manifest retains the reported name and records this classification as a
corroborated prefix. It forces `PARTIAL`: an alternate-name interface may
carry an unknown vendor tail and exposes no size field with which to disprove
that. An entry that fails corroboration remains present-but-undecoded vendor
evidence. Discovery still never calls `C_GetInterface`; it only compares
`dlsym` export addresses with already acquired, bounded table bytes.

Replace the shared unsafe `read_fn_pointers(base, fields)` with a safe
`read_fn_pointers(bytes, fields) -> Result` that uses checked offset arithmetic
and rejects any field not wholly contained in the supplied snapshot. Keep the
existing unsafe `detect_null_functions()` for the proxy's in-process live-table
capability scan; changing that separate trusted call path buys no safety for
scope. Add the malformed-pointer and short-slice regressions in the shared
crate, publish one reachable successor to the currently pinned
`7c5c86043820eb3795f40c65a36ce961cdfd26c5`, then update both scope git
dependencies to that same revision. No broader crate reorganization is needed.

### Bounded table reads

Legacy tables reporting 2.00 are walked as the 67-field prefix ending at
`C_CancelFunction`. The published 2.01 header adds only the final
`C_WaitForSlotEvent` slot; 2.01, 2.10, 2.11, 2.20, 2.30, and 2.40 therefore
walk the complete 68-field base table. This version-to-length decision lives
in shared `tables_for()`: it reuses the first 67 entries of
`FUNCTION_LIST_FIELDS` rather than copying their names into another catalog.

Legacy stamps 3.0, 3.1, and 3.2 are accepted as a compatibility case for
nonconforming providers, but only the 68-field legacy prefix is walked and the
surface forces `PARTIAL`; their 3.x extensions still come solely from standard
interfaces. Unknown 2.x revisions above the published range likewise walk the
known 68-field prefix and force `PARTIAL`. Other versions produce
`WalkOutcome::Unreadable`. The exact reported version is always retained as
evidence.

Table bytes are copied with a bounded read from `/proc/self/mem` into owned
memory before the shared `read_fn_pointers()` helper is called. The copy size
is computed from the selected shared `FnField` tables. A short or unreadable
table produces an explicit unreadable walk outcome instead of an unchecked
dereference or helper crash. Interface version selection continues to use the
shared `tables_for()` authority.

### Schema

The manifest schema first became `p11scope-manifest/2`, then
`p11scope-manifest/3`, and advances to `p11scope-manifest/4` in the
review-corrected provenance closure. Version 2 added
`Resolution::UnusableFile { reason, path_hex }` and
`WalkOutcome::Unreadable { detail }`. Version 1 manifests are rejected with a
rediscovery instruction because they can contain the unsound identity and
table-read results this release fixes. Version 3 adds an always-computed
whole-file SHA-256 beside the reporting build ID and requires fresh trusted
discovery to reproduce every function-role/object/offset tuple before attach.
Version 4 adds the complete bounded provenance-object closure required to make
one rediscovery pass authoritative under pre-existing read leases; see
`docs/superpowers/plans/2026-08-13-manifest-provenance.md`.

## 4. Evidence, output, and I/O

- An interface-list enumeration error forces `PARTIAL`; absent and empty are
  complete outcomes when their facts are successfully established.
- Both profile modes render `capture.module` as `{path, build_id}` through one
  `CaptureMeta` path.
- The corrective baseline profile schema became
  `pkcs11-scope/observed-profile/v1.3` for broadened session retirement,
  process tracking, and 3.2 semantic/async evidence. Metrics became
  `pkcs11-scope/observed-profile/v1-metrics`; changing `capture.module` from a
  string to an object was a breaking shape change, not a point release. The
  privacy amendment linked at the top advances these to v1.4 and
  v1.1-metrics; older identifiers are never reinterpreted.
- The v1.3 schema carries an explicit v1.2 migration note: `sessions.closed`
  now includes close-all, Finalize, and observed process-death retirement;
  `sessions.inherited` is new; and balance is `opened + inherited - closed`.
  Consumers computing leak rates must not compare those fields directly across
  the schema boundary. `functions[].errors` excludes `CKR_PENDING` in v1.3;
  `pending_returns` and exact `rv_counts` retain that fact separately, while
  async semantic transitions are applied at completion rather than the first
  pending return.
- Evidence adds the start/RV-map, cgroup-scope, process-tracking,
  state-reconciliation, session-cancel,
  authentication-state, async-target, async-orphan/eviction,
  operation-state-import, semantic-capture, and pending-at-end counters named
  above. Every counter representing lost or ambiguous state forces `PARTIAL`;
  ordinary use of a tracked async operation does not.
- The all-attach-failed summary prints the actual failed/attempted count.
- Trace output uses fallible writes. File write or flush failure exits nonzero.
  A stdout broken pipe closes that sink without a panic; an `-o` sink continues
  and receives the final drain and loss line. Other stdout failures propagate.
- Raw pid/tid and exact per-call latency remain trace-only because they are
  required for per-thread investigation. The privacy allowlist documents their
  correlation and timing risk, the bounded-investigation rationale, and output
  handling expectations instead of claiming only bucketed aggregate latency is
  exposed.
- The privacy allowlist also names every newly readable argument word,
  function-name validation, output-pointer nullness, and expanded template
  position. It states whether the value is reduced, dereferenced through an
  existing allowlist, or kept internal. New PIN, username, signature,
  plaintext, ciphertext, associated-data, async-data, and key-material
  canaries prove those buffers never enter maps or output.

## 5. Build, gates, scripts, and release

### Provider compatibility

Reuse the sibling workspace's provider paths, fixture conventions, and
published interface expectations, but run `p11scope-discover` directly against
each module. A passing proxy backend test is useful prior evidence, not a scope
result. The matrix records `PASS`, `FAIL`, or `SKIP(reason)` per provider and
surface; a skip never supports a compatibility claim.

The mandatory deterministic lanes are the generated C provider and the pinned
`pkcs11-proxy-ng` shim. The shim must enumerate legacy 2.40 and standard
2.40/3.0/3.2 as 68/68/92/104 without a running daemon; its test process sets
the shim's existing `PKCS11_PROXY_CONNECT_ATTEMPTS=1` test budget so a
capability probe fails quickly. Scope does not special-case or mutate provider
behavior.

The real-provider lane covers every configured module from the shared test
environment: SoftHSM2, NSS softokn, BouncyHSM, and Kryoptic. Current expected
surface evidence is intentionally provider-specific: SoftHSM2 may expose only
legacy 2.40; NSS preserves its standard 2.40/3.0 and vendor interfaces;
BouncyHSM preserves 2.40/3.1/3.2 and is not relabeled as a nonexistent literal
3.0 interface; Kryoptic is asserted only when provisioned. Ubuntu release CI
must provision and pass SoftHSM2 and NSS. Other providers may be skipped only
with explicit environment evidence, and release notes name only providers that
actually passed. Alpine runs the deterministic fixture and its available
SoftHSM build. No proxy-specific unnamed-interface fallback is copied into
scope, and discovery never calls `C_GetInterface`.

The outer build gives the inner eBPF cargo invocation a dedicated target
directory under `OUT_DIR`, then embeds only the artifact from that directory.
The skip escape hatch is removed. Cargo rerun inputs include the eBPF lockfile,
toolchain file, and both eBPF crate manifests and sources.

The induced-gap/build check inspects the freshly built eBPF object's `EVENTS`
map and proves default and small-ring builds contain different expected
capacities. It no longer relies on call volume alone to imply that the feature
was embedded.

The canary gate gains a second capture using the existing blocking fixture:

1. block inside `C_Login` while its sentinel PIN is live;
2. obtain the observer's real PID and enumerate `/proc/<pid>/fdinfo` to get
   this run's BPF map ids, then select and validate its `START` map by id;
3. poll until the map is demonstrably nonempty;
4. dump and scan it before releasing or killing the workload.

No global map-name search or before/after name diff is accepted: either could
select a stale or concurrent capture. Additional blocked calls exercise every
descriptor argument position, including stack argument 6, while arguments 7
through 9 carry negative canaries; the map scan must remain clean. Dedicated
3.0/3.2 calls cover `C_LoginUser`, message APIs, `C_VerifySignatureInit`,
authenticated unwrap, and async function-name matching. The test-only
small-ring BPF variant also gives `START` one entry, drives two concurrent
calls, and asserts `start_map_drops > 0` and `PARTIAL` so the map ceiling cannot
become silent again.

The scanner's positive control is encoded as bpftool-style `0xHH` tokens and
must be found through the same reconstruction path used for map dumps. Release
builds run the canary gate.

Release output contains `p11scope-discover` (the glibc helper used by the
documented command) plus the explicitly suffixed glibc and musl copies. The
packaged `p11scope discover` path is smoke-tested.

Bench and matrix scripts delete their expected outputs before each run, require
fresh nonempty artifacts, preserve and check observer exit status, and kill and
wait for every background process from traps. `wait` status is captured inside
an `if`, where `set -e` cannot bypass it. `spike/check.sh` rejects missing
arguments.

Documentation is corrected to say discovery loads and calls the provider,
attribute the kernel floor to attach cookies, describe the new schemas and
session semantics, and use stable symbol/function citations instead of source
line numbers in the privacy allowlist.

## 6. Regression-suite design

Every finding gets a test at the lowest layer that can prove the behavior.
Tests must first fail against the reviewed implementation, then pass after the
shared fix.

### Layer A — pure and fast (`cargo test`)

- exact shared 67/68/92/104 boundaries and a descriptor-exhaustiveness test
  proving every published standard slot is explicitly semantic or explicitly
  count-only; the sibling precursor separately pins the
  110/104/six-function/11-mechanism-gap OASIS inventory before its revision is
  consumed;
- 424 distinct known-version targets fit the 512-slot ABI and target 513 is
  rejected before load without truncating the plan;
- table-driven operation transitions for all classic, message, signature,
  cancellation, direct-key, lifecycle, and async descriptors; no suffix-based
  inference remains;
- interleaved operations, combined updates, non-operation session calls,
  every named termination bucket, output-length queries, buffer-too-small,
  terminating and non-terminating errors, message-process reuse,
  `CKF_END_OF_MESSAGE`, object-search presence, single/multi-flag session
  cancellation (including find plus crypto), alias refusal,
  all nine direct key mechanisms, failed `C_Login`/`C_LoginUser`, handle reuse,
  successful login/login-user/logout ambiguity, async-session opens, opaque
  operation-state restore, close-all slot isolation, Finalize, and explicit
  process retirement;
- operation-not-initialized, session-closed/invalid, and
  Cryptoki-not-initialized reconciliation before mechanism attribution;
- pending OpenSession/init/update/final/direct calls, unreadable pending-open
  handles, repeated `C_AsyncComplete`, get-id / close / Finalize / join,
  cancellation, duplicate/orphan keys, bounded eviction, and pending-at-end

### Layer B — unprivileged fixture processes

- wrapper-to-backend dependency resolution;
- relative/basename decoy rejection;
- lazy backend loading;
- invalid, unterminated, and unreadable interface-name/version pointers, which
  become evidence without crashing either shared acquisition or discovery;
- alternate and null interface names with valid standard export anchors, plus
  deceptive version-stamped vendor tables whose anchors do not match;

- pidfd readiness after whole-process exit, close-on-retire, and deterministic
  low-budget demotion to start-time polling;
- packaged helper lookup without invoking BPF.

Fixtures are deterministic C providers compiled by the existing integration
test pattern. The direct SoftHSM/NSS/BouncyHSM/Kryoptic matrix supplements

### Layer C — privileged live-BPF gates

- exact end-to-end function and corrected mechanism counts;
- re-entrant same-thread/same-slot calls and an induced tiny RV map, each with
  nonzero loss evidence and `PARTIAL` rather than silent overwrite/drop;
- a ten-argument native call that proves x86-64 register/stack argument reads,

- exact-map-id, nonempty live-`START` privacy scan, output-pointer sentinels,
  and hex-path positive control;
- embedded default/small ring capacities;
- trace final drain/loss behavior with a real pipe and file sink.

do not silently skip in a release run.
